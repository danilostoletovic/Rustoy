# Rustoy technical design

This is an architectural reference. See [implementation status](STATUS.md) for what has shipped or passed verification. The upstream design links below point to the historical checkout.

## What Ventoy actually does

The synthetic device is a preboot transport. Once the OS leaves UEFI boot services, it must reopen the selected image using its own storage drivers. Linux mounting the ISO and Windows Setup opening the install image are separate milestones from any EFI entry point running.

## Workspace and media layout

| Crate | Responsibility |
| --- | --- |
| `rustoy-host` | Rust CLI for image creation, inspection, installation, updates, integrity metadata, and offline signing. Host disk APIs stay behind platform-specific adapters. |
| `rustoy-uefi` | `x86_64-unknown-uefi` application, keyboard menu, firmware protocol adapters, device lifetime and boot dispatch. |
| `rustoy-fs` | Checked GPT and filesystem access. Read-only exFAT image storage shared with host tooling. Use firmware FAT access on the ESP and a Rust writer for formatting. |
| `rustoy-iso` | ISO9660, El Torito and later UDF readers. Bounded virtual image views, sparse read overlays and boot profile discovery. |
| `rustoy-security` | Manifest serialization and validation, digest verification, and host-only PE/COFF Authenticode signing and verification. Use reviewed Rust cryptographic dependencies. |
| `rustoy-linux`, `rustoy-windows` | Small, versioned boot adapters. Add guest-side Rust helpers only where necessary. The Windows guest executable uses the supported WinPE API subset. |
| `rustoy-integration` | Host-side QEMU harness, fixture inventory, guest outcome probes and artifact capture. |

Shared parsers and verification logic use `no_std` with bounded allocation. Partition layout is GPT with a FAT32 ESP containing `EFI/BOOT/BOOTX64.EFI` and an exFAT data partition for unchanged ISO files, including files larger than 4 GiB. Identify the data partition as a sibling of the boot ESP via the boot device and GPT identity. Discover regular ISO files under the data volume, bound enumeration and sanitize display names. The menu supports keyboard navigation, rescan, boot and return to firmware. A canceled or failed boot tears down temporary protocol handles before redisplaying the menu.

Use positional byte reads over the actual file as the common interface. The exFAT reader translates file offsets through contiguous allocation or FAT chains. Keep physical block size, optical sector size and file length separate. Reject invalid allocation chains, out-of-range extents, integer overflow, overlapping overlay regions and unsupported sector or filesystem layouts. Use checked conversions on both 512-byte and 4 KiB backing devices. Pin protocol context for the duration of child execution, keep FFI and firmware callback pointers in a small audited boundary, and retain or clean up state according to UEFI ownership rules. No assembly is planned.

Start the host installer with newly created disposable raw files. Later, expose inspect and plan on real disks, then explicitly selected removable-device installation. Resolve stable device identity again after exclusive open and volume locks, verify layout and write boundaries, flush and read back. Stage and verify signed ESP updates before replacing the boot file. Keep recovery instructions for interruptions on FAT; do not assume file replacement is power-loss atomic. Upgrades preserve the data partition and ISO files.

## Linux boot path

Start with a pinned x86_64 Debian Live image whose stock initramfs supports `findiso` and can mount the chosen backing filesystem. Confirm both from the actual image and use an isolated FAT data fixture to diagnose exFAT support if needed. FAT-only success is recorded against that fixture and does not qualify the installed exFAT layout.

Read the EFI-stub kernel and initramfs into bounded buffers directly from the ISO. Invoke the kernel through firmware LoadImage and StartImage and pass the initramfs via the Linux EFI initrd media device path and LoadFile2. Supply a release-specific command line including `boot=live` and the selected `findiso` path. Limit initial paths to forms the guest parses unambiguously. With duplicate path names on different disks, test the guest's resolution rules and gate secure mode on identity-bound recovery and verified reads. The stock live initramfs must mount the USB filesystem, loop-mount the original ISO, and mount the live root from it. The guest supplies the persistent view after ExitBootServices. [Linux EFI stub](https://docs.kernel.org/admin-guide/efi-stub.html) · [Debian live-boot](https://manpages.debian.org/trixie/live-boot-doc/live-boot.7.en.html)

Expand through explicit profiles using stock ISO loopback parameters where available. For images that cannot reopen their source this way, evaluate a Rust initramfs helper that resolves GPT identity and presents a read-only file loop or a validated device-mapper view. Use normal Linux kernel interfaces. Do not copy Ventoy's shell hooks or interpret general GRUB scripts. Profiles independently specify filesystem availability, kernel/initrd discovery, command-line requirements and guest media recovery.

## Windows boot path

1. Pin official Windows 10 and 11 x64 installer fixtures. Validate the x64 El Torito boot catalog and embedded FAT image. Publish the optical Block I/O view and serve the boot filesystem through a Rust-backed read-only UEFI interface where firmware lacks appropriate filesystem support. Confirm the Microsoft EFI entry point retains a usable device path and can read the BCD, SDI and WIM from the synthetic medium. Add narrow UDF support when the fixture requires it.
2. Prove unmodified boot-manager-to-WinPE startup first. Then test an in-memory WIM overlay for the exact boot index with an added Rust launcher and documented `winpeshl.ini` startup configuration. Preserve signed Microsoft loaders and leave the USB ISO bytes unchanged. The ISO/UDF view must advertise the new WIM size and read the replacement resources consistently. Generate the sparse overlay offline in the host tool if boot-time WIM reconstruction exceeds the memory budget. Support only measured compression and metadata variants. Measure peak RAM independently of ISO size. [WinPE app startup](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/winpe-create-apps?view=windows-11)
3. Pass a bounded handoff descriptor into the approved WinPE overlay, identifying the backing data partition, exact file path and expected content. The launcher waits for USB enumeration, resolves the original file, and attempts native read-only ISO attachment. Treat applicability of the virtual disk APIs and their providers in each WinPE fixture as a test gate. Check the mounted source and start Setup from the intended medium, with a diagnostic failure if it cannot read `sources/install.wim`, `install.esd` or supported split media. If the native API is unavailable, document the failing versions and evaluate a supported, signed Rust storage component separately. [OpenVirtualDisk](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-openvirtualdisk)

The Windows feasibility gate is a completed install to a disposable target with the ISO present only as a file on the USB image. A WinPE prompt or successful boot-manager launch is intermediate evidence. Do not bypass Windows 11 platform checks.

## Secure Boot and trust

**Custom enrolled keys.** Sign the Rust EFI application offline using PE/COFF Authenticode and enroll its certificate in firmware `db` through the platform owner's enrollment path. For production, preserve the platform PK, KEK, required Microsoft/OEM entries and existing `dbx` where the firmware supports additive enrollment. Use separate test identities and private OVMF variable stores. Keep private keys off USB media. Confirm deployed certificates and revocation state on the target. Every EFI child goes through firmware LoadImage and StartImage with an accurate device path. Any non-successful admission aborts that launch. Leave firmware verification, boot service callbacks and revocation policy intact. [UEFI Secure Boot and driver signing](https://uefi.org/specs/UEFI/2.11/32_Secure_Boot_and_Driver_Signing.html)

**Authenticate data that controls execution.** Embed a separate manifest verification public key in the signed EFI binary. An offline signer authorizes exact ISO bytes, the selected boot profile, immutable command line, initrd and any Windows overlay or guest helper. Use a versioned canonical manifest with bounded signed chunk digests, verified from the same bytes served to consumers. Bind overlay input and final view to the same approval. Paths and GPT IDs locate media but provide no integrity on their own. The verified boot path forbids arbitrary initrd, argument and overlay changes. Only accept a kernel or boot manager that also passes firmware admission. Never sign data automatically merely because it was found on the USB.

**After ExitBootServices.** Firmware signature verification does not cover live root or Setup data. For Linux, require an authenticated initrd to establish a persistent verified read path, such as a signed dm-verity root over a read-only loop device with externally prepared hash data. The stock `findiso` path can qualify the first boot milestone. It cannot qualify the secure ISO profile without an equivalent persistent integrity mechanism. For Windows, validate the signed WIM overlay and bind the startup helper and source descriptor before preboot consumption. Before claiming end-to-end integrity, show that Windows code integrity and the storage path enforce the approved helpers and source bytes through Setup. A one-time file digest before native attach leaves a mutable-media gap. Until that gap is closed, report only the verified preboot scope or reject the profile in secure mode. Measurements may supplement enforcement but do not replace it.

**Updates and negative tests.** Define offline signing authorization, staged trust-root rotation, evidence of revocation and recovery before release. Treat previously approved bootloaders and manifests as replayable until a platform-backed minimum version or explicit revocation is demonstrated. Test unsigned and tampered EFI, an enrolled image revoked in `dbx`, wrong manifest key, modified command line/initrd/overlay, changed USB blocks after preboot, and a missing source device. Verify both that the operation fails and that the untrusted stage never runs.

**Factory-key compatibility.** Stock OEM trust stores cannot admit a Rustoy binary signed only by a Rustoy key. Direct signing by an already trusted CA is an external feasibility and distribution question. A supported third-party shim with owner MOK enrollment would still require owner trust setup. A vendor-authorized shim embedding a Rustoy certificate would require upstream and signing-program acceptance, revocation planning and verification on the target OEM trust stores. Keep these as investigations and report actual firmware, enabled trust roots and key enrollment for every result.
